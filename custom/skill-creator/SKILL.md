# Skill 设计与迭代工作说明书 (Skill Creator)

本 Skill 的目标不是帮你写一段“更长、更复杂的万能提示词”，而是像给**刚入职但极聪明的同事编写工作说明书（SOP）**一样，构建一套结构清晰、可反复执行、可持续迭代的能力包。

---

## 一、核心认知与铁律

1. **Skill 是工作说明书（SOP），不是超长 Prompt**
   - `Prompt` 解决“这一次怎么做”；`Skill` 解决“以后遇到这类任务都应该怎么做”。
   - 严禁通过无休止堆砌要求和注意事项来写 Skill。先理清**从哪开始 → 经过哪些步骤 → 每步需要什么信息 → 最终交付什么结果**，再动笔写文件。
2. **严格分层，保持 `SKILL.md` 高信噪比**
   - `SKILL.md`（必选）：只保留**触发时机、核心任务目标、标准流程步骤（SOP）、长期不变的铁律、交付标准**。
   - `references/`（按需）：存放详细规则、边界情况、长篇参考案例、领域知识。
   - `scripts/`（按需）：存放可自动执行的确定性工具脚本（抓取、转换、提取、校验等）。
   - `assets/`（按需）：存放需要重复使用的模板、素材、配色方案等。
   - *注：子文件夹按任务复杂度按需创建，不强求全有。*
3. **破坏性更新原则（删旧替新，拒绝打补丁）**
   - 修改或迭代规则时，**直接删除旧规则，用清晰的新规则原地替换**。
   - 严禁在文件中写“不要再使用之前的某规则”或同时保留新旧两个版本，杜绝前后矛盾。

---

## 二、执行流程（SOP）

收到用户创建或优化 Skill 的请求时，先判断当前处于哪个阶段，按对应路径执行：

### 阶段 1：模式路由（选择创建方法）

根据任务复杂度与当前上下文，二选一进入创建流程：

#### 路径 A：先跑通流程，再沉淀为 Skill（适合轻量/线性任务）
*适用场景：文章写作、标题创作、信息整理等轻量任务，或用户已经在当前对话中和你一步步跑通了一次真实任务。*
1. **流程回溯**：如果还没跑通，先不写 `SKILL.md`，而是带着用户从第一步开始手动跑通一次完整任务，遇坑填坑，直到产出满意的最终结果。
2. **SOP 提炼**：回溯刚才实际验证过的每一步，剔除试错弯路，提取出确定的**输入 → 步骤 → 验证过的规则 → 输出**。
3. **防遗漏核对**：若此前经历了多轮复杂修改，先列出提取到的规则清单让用户确认有无遗漏，再生成正式 Skill 文件。

#### 路径 B：先搭五要素框架，再实测迭代（适合复杂/多链路任务）
*适用场景：自动化剪辑、多步工程流、跨工具协同等复杂任务，或从零开始设计新 Skill。*
1. **五要素对齐**：不需要让用户一开始想清楚所有细节，只需引导或帮用户明确以下 **5 件事**：
   - **任务目标**：这个 Skill 具体要完成什么任务？
   - **触发条件**：什么时候应该调用这个 Skill？
   - **核心步骤**：整个流程有哪些步骤（先做什么、后做什么、每步要什么信息）？
   - **重要规则**：有哪些必须遵守的核心红线？
   - **交付结果**：最后要输出什么格式、做到什么程度才算完成？
2. **生成 V1 基础框架**：使用 `assets/SKILL-template.md` 或运行 `node scripts/scaffold-skill.js` 生成第一版最小可用框架。
3. **引导实测闭环**：明确告知用户“V1 只是基础框架”，引导用户新开一个真实任务调用该 Skill 测试，并按以下三问收集反馈进入阶段 2：
   - 哪个步骤没有执行？
   - 哪个规则理解错了？
   - 哪个结果不符合要求？

---

### 阶段 2：迭代与精修（两大核心动作）

当用户在真实任务中发现 Skill 卡壳、效果变差或需要升级时，执行以下两个动作：

#### 动作 1：用成熟工具补齐能力短板（精准移植，拒绝盲目搬运）
当 Skill 卡在某个确定性环节（如网页抓取、字幕提取、格式转换、音视频处理、PDF 解析等）时：
1. **定位工具缺口**：判断这属于“缺少工具”而非“提示词不够长”。
2. **搜索与三步拆解**：寻找 GitHub 或生态中的成熟开源方案，**严禁盲目复制整个项目**。先向用户输出三步分析：
   - 该工具解决了什么核心问题？
   - 其中哪段核心代码或逻辑适合当前任务？
   - 需要安装哪些最小依赖？
3. **最小化集成**：只把真正需要的代码/脚本提取并封装进 `scripts/`，并在 `SKILL.md` 的对应步骤中写明调用命令。

#### 动作 2：内容分层瘦身与规则替换（防止越改越蠢）
每次修改已有 Skill 时，执行一次体检（可运行 `node scripts/scaffold-skill.js --audit <skill目录>`）：
1. **剥离超长内容**：若 `SKILL.md` 中混入了具体长篇案例、复杂细分规则或大段代码，将其下沉到 `references/`、`scripts/` 或 `assets/`，`SKILL.md` 中只保留一句话索引链接。
2. **清理补丁痕迹**：检查是否存在“注意：不要再用旧版……”、“补充修正……”等历史补丁语句。将旧规则彻底删除，原地改写为唯一、无歧义的当前规则。
Detailed 对比清单与正反例见 [references/methodology-and-anti-patterns.md](references/methodology-and-anti-patterns.md)。

---

## 三、交付标准

每次完成 Skill 的创建或迭代后，向用户交付以下内容：
1. **清晰的目录树**：展示生成的 `SKILL.md` 及按需创建的 `references/`、`scripts/`、`assets/` 文件路径。
2. **五要素摘要**：一句话总结该 Skill 的触发条件、核心 SOP 步骤与交付物。
3. **下一步实测建议**：给出一个可直接复制用于测试该 Skill 的真实任务 Prompt。
