# Skill 设计方法论与反模式参考手册

本参考手册用于辅助 `skill-creator` 在创建和审计 Skill 时对照检查。

---

## 一、Prompt 与 Skill 的本质区别

| 维度 | 普通 Prompt（一次性指令） | Skill（可复用的工作说明书 / SOP） |
|---|---|---|
| **解决的问题** | “**这一次**怎么做” | “**以后遇到这类任务**都应该怎么做” |
| **角色隐喻** | 临时给路人派发的一张便签 | 给聪明但刚入职的新同事准备的《岗位标准作业说明书》 |
| **组成形态** | 纯文字对话指令 | `SKILL.md` 主流程 + `references/` 细则案例 + `scripts/` 自动化脚本 + `assets/` 模板素材 |
| **演进方式** | 每次开新对话重新描述，容易遗忘 | 一次次踩坑经验持续沉淀，最终变成个人工作系统 |

---

## 二、常见反模式（为什么你的 Skill 越改越难用？）

### 反模式 1：把 `SKILL.md` 当成垃圾桶不断堆砌
- **症状**：每次遇到问题就往 `SKILL.md` 末尾追加一段“注意事项 15”、“补充规则 16”，文件长达上千行，混杂着主流程、三个月前的特例、长篇范文和报错补丁。
- **后果**：AI 注意力被稀释，忘记前面说过的核心步骤，甚至因为规则冲突直接回答“对不起，我做不到”。
- **解法（严格分层）**：
  - `SKILL.md` 只留**骨架**（触发时机、核心步骤 SOP、长期不变的铁律）。
  - 详细规则和长案例移入 `references/`，在主文件里写 `详见 references/xxx.md`。
  - 重复使用的模板、配色、静态素材移入 `assets/`。
  - 固定逻辑写成脚本放进 `scripts/`。

### 反模式 2：打补丁式改规则（新旧并存、前后矛盾）
- **症状**：修改规则时，保留了原来的旧规则，然后在下面加一行：`【重要更新】不要再使用上面的 XX 规则，改用 YY 规则`。
- **后果**：大模型对否定句和冲突指令极易产生混淆，经常还是按旧规则执行。
- **解法（破坏性更新 / 删旧替新）**：
  - ❌ 错误写法：`第一步按 A 方式输出。注意：不要再使用之前的 A 方式了，现在必须用 B 方式。`
  - ✅ 正确写法：（直接删掉 A 的一切痕迹）`第一步：按 B 方式输出。`

### 反模式 3：还没理清 SOP 就直接写 `SKILL.md`
- **症状**：自己都没想明白这件事从哪开始、中间分几步、每步要什么输入，就让 AI 硬编一个 Skill。
- **后果**：生成的 Skill 全是正确的废话（如“确保高质量输出”、“注意逻辑清晰”），落地时一步都走不通。
- **解法**：
  - 轻量任务：**先手动带 AI 跑通一次真实任务**，跑通后再提炼。
  - 复杂任务：**先对齐五要素**（做什么、何时触发、有哪些步骤、核心规则、输出什么），搭好 V1 框架后立刻进真实任务测试。

### 反模式 4：缺工具时死磕提示词，或盲目照搬整个开源项目
- **症状**：遇到网页抓取、字幕提取、音视频剪辑、PDF 处理、格式转换等任务卡住时，要么反复改提示词逼 AI 凭空处理，要么把 GitHub 上整个几百兆的项目原封不动塞进 Skill。
- **后果**：提示词解决不了工具层面的缺失；而照搬整个项目会导致依赖爆炸、结构混乱。
- **解法（三步精准移植）**：
  1. 分析该开源工具解决了什么具体问题？
  2. 提取其中真正适合当前任务的**核心代码或逻辑**。
  3. 明确**最小依赖**，将其精简封装进 `scripts/` 目录供 Skill 调用。

## 三、Skill 迭代验收清单（Checklist）

在交付或更新任何 Skill 前，逐条核对：
- [ ] **五要素齐备**：触发时机、任务目标、SOP 步骤、核心规则、交付结果是否一目了然？
- [ ] **主文件精简**：`SKILL.md` 是否控制在高信噪比范围内（建议 ≤ 200 行），没有把长篇案例和底层代码硬塞进去？
- [ ] **无历史补丁残留**：全文是否彻底清除了“不要再用旧规则”、“之前版本作废”等冲突表述？
- [ ] **工具边界清晰**：需要确定性计算、文件处理、外部抓取的步骤，是否已经抽离为 `scripts/` 脚本？
